# SPIKE-04: APK permissions and Samsung execution behaviour

| | |
|---|---|
| Date | 2026-10-13 |
| Jira | SCRUM-12 |
| Result | **pass on adb routes for both pilot phones; file installs blocked** (D-14). Z Flip 5 in `spike-04-2026-10-13-z-flip-5.md`. One anomaly still unexplained |
| Question | What do SMS receipt, notification-listener access and posting own notifications each require on the pilot phones, and what happens to background receipt after denial, revocation, force-stop, reboot and battery restriction? |

## Setup

| | |
|---|---|
| Device | Samsung Galaxy S25 Ultra, model SM-S938B, Android 16 (API 36), One UI 8.0.5, build `BP4A.251205.006.S938BXXSCCZH1`. Dual SIM (Airtel, Jio) |
| App build | `:spikes` debug build, commits `9c56b9e` and the lab fix after it (`com.expensetracker.spikes`) |
| Install route | **A:** `adb install` (installer null, initiated by `com.android.shell`). **B:** APK copied to Downloads and opened from My Files |
| Data used | Real bank SMS (HDFC credit alerts, redacted by the app before logging); shell-posted test notifications; the app's own test notification |

What the test app does: declares only `RECEIVE_SMS` (no `READ_SMS`, so no inbox import) and `POST_NOTIFICATIONS`; has a notification listener that reads text only for an explicit package allowlist (default: itself and the adb shell) and counts everything else as "ignored" without storing content; logs only redacted text.

## Steps and observations

### Consent and denial (route A)

| Capability | What the user saw | Result |
|---|---|---|
| SMS receipt | Android prompt "Allow Spikes to send and view SMS messages", buttons Allow / Don't Allow. This is Samsung's group wording; the app asks for receive only | Granted by one tap; status updated on return |
| Notification access | In Settings, one popup with an Allow button, then the toggle changed. **No "restricted setting" detour through App info on this route** | Enabled and connected |
| Posting own notifications | Prompt "Allow Spikes to send you notifications?", Allow / Don't Allow | Allowed; test notification appeared in the shade (no pop-up banner: default importance channel) |

### Independence, denial and recovery

| Test | Observation |
|---|---|
| Revoke only SMS | Only that status changed; listener and posting untouched; manual entry still saved; in-app feedback shown |
| Ask again after revocation | Prompt returned |
| Deny the prompt, ask again | Nothing happens (`USER_FIXED` set). Recovery is only via Settings: app button → App info → Permissions → SMS → Allow (4 screens). Status was correct on return |
| Revoke only posting | Only that status changed. "Post test" shows the in-app message "Posting is blocked, so this message is shown in the app instead", no notification. Manual entry still saved |
| Revoke only notification access | Only that status changed; `listener-disconnected` logged. Re-enabling showed the same Allow popup again and reconnected |

### Background behaviour

| Test | Result |
|---|---|
| Real SMS received with the app closed (process alive via the bound listener) | Received, delay about 2.8 s from the bank's timestamp |
| RCS chat sent from the same phone | **Not received.** Google Messages showed it as RCS, which is not an SMS broadcast. Bank alerts are SMS, so this is expected; any bank sending RCS business messages would need the notification path |
| Force-stop with the listener enabled | The system restarted the listener within seconds on its own; shell notification captured |
| Force-stop, first attempt, 18 s after re-enabling access | The grant was gone from the enabled list and nothing rebound. Not reproduced on a second attempt. **Unexplained; to watch** |
| Reboot, app never opened | Listener reconnected by itself; permissions persisted; a real SMS afterwards was captured (3.5 s) |
| Battery set to Restricted (Settings > Apps > Spikes > Battery; options Unrestricted / Optimised / Restricted; no warning) | Samsung applied it after the screen turned off: standby bucket 45, `RUN_ANY_IN_BACKGROUND` = ignore. Listener still captured notifications. SMS captured twice (3.2 s, 1.8 s) |
| Restricted, listener **off**, app force-stopped, then a real SMS | SMS arrived on the phone and the app **did not receive it** (process stayed dead) |
| Same state, then the app opened once and put in the background, then a real SMS | Received (2.3 s) |

### Install route B (file manager)

| Step | Observation |
|---|---|
| Open the APK from My Files | Standard installer prompt "Install this app? Spikes". No unknown-source or Auto Blocker screen appeared first |
| Confirm install | **Blocked.** Message: "App blocked to protect your device. This app can request access to sensitive data. This can increase the risk of identity theft or financial fraud." Only an **OK** button. No "install anyway", no details |
| Result on the phone | The package was **not installed** (`pm list packages` empty) |

This matches Google's Play Protect "enhanced fraud protection" pilot for India: installs from browsers, messaging apps and file managers are blocked automatically when the app declares SMS (`RECEIVE_SMS`, `READ_SMS`), notification-listener or accessibility permissions, with no user override. `adb install` from a PC is not affected. The app's own capture design needs exactly those permissions, so a private APK handed to a user as a file cannot be installed by tapping it on this phone.

## Result (so far)

- Posting, SMS receipt and notification access can each be granted, denied and revoked independently on the S25 Ultra, with manual entry unaffected.
- Notification access via the adb route needs one extra confirmation popup but no App info detour.
- **A user cannot install this app by opening an APK file on the S25 Ultra.** Play Protect blocks it because of the declared SMS and notification-listener permissions. Only `adb install` from a PC worked. The pilot therefore uses `adb` only (D-14).
- SMS receipt survives reboot, the Restricted battery setting and a missing listener. It does **not** survive a force-stop until the user opens the app again. No code can change that; it needs a user-facing recovery message.

## Decision or change this causes

- Setup copy must explain that SMS permission wording is broader than what the app uses ("send and view").
- Capture health must show "Open the app to resume SMS capture" after a force-stop; no promise of background execution (CAP 01).
- Recovery from a denied permission is Settings only, so the readiness screen needs a direct "Open app settings" action.
- Non-allowlisted notifications must be ignored with no content stored (CAP 02); the test app proved the pattern after an over-collection mistake on 13 October that was cleared the same day.
