# SPIKE-05: encrypted storage and portable export

| | |

| Question | Can the app keep data in an encrypted database whose key lives in the Android Keystore, and still export and restore it on a clean install without the old device key? |

## Setup

| | |
|---|---|
| Device | Android Studio emulator, `Medium_Phone_API_36.1`, Android 16 (API 36), x86_64. **Not a target phone.** |
| App build | `:spikes` debug build on top of commit `51a2490`; the commit that adds this file holds the exact code |
| Accounts or data used | None. Test rows only: three fake expenses |
| Pinned versions | Room 2.8.5, SQLCipher for Android (`net.zetetic:sqlcipher-android`) 4.19.1, KSP 2.3.12, BouncyCastle `bcprov-jdk18on` 1.86, Kotlin 2.2.10, AGP 8.13.1 |

## What was built

- `KeystoreKeyProvider`: a random 32-byte database passphrase, stored only as an AES-GCM blob wrapped by a non-exportable Android Keystore key.
- `EncryptedDb`: Room with the SQLCipher open-helper factory.
- `PortableExport`: password-based export. A key is derived from the password (PBKDF2-HMAC-SHA256 at 600,000 rounds, or Argon2id at 19 MiB, 2 passes, 1 lane), then AES-256-GCM. The versioned header (format version, KDF and its parameters, salt, nonce) is authenticated, so changing any byte of it fails the open. A file cannot ask for more than fixed limits of work or memory.
- `ExpenseBackup`: exports rows as data (not a copy of the database file) and restores them into a fresh database.

## Steps and observations

| Check | How | Observed |
|---|---|---|
| Rows persist across close and reopen | Insert, close, open again with a new key provider instance that unwraps the key from disk | Pass |
| File on disk is encrypted | Read the raw `.db` bytes | No `SQLite format 3` header; merchant text not present. Pass |
| Wrong key cannot read it | Open with 32 random bytes and query | Throws. Pass |
| Stored key blob hides the passphrase | Read `files/spike_test_key.bin`; compare | Passphrase not present; the same passphrase comes back on the next load. Pass |
| Keystore key is not exportable | `SecretKey.encoded` | `null`. Pass |
| Reset gives a new key | Delete blob and Keystore entry, ask again | Different passphrase. Pass |
| Export then restore on a "clean install" | Export, delete database, blob and Keystore key, create new key, restore | Same three rows back; the new key differs from the old one. Pass for both PBKDF2 and Argon2id |
| Wrong password on restore | Restore with another password | `WrongPasswordOrCorrupt`; database stays empty. Pass |
| Export tampering and format (unit tests, JVM) | 10 tests: round trip for both KDFs, wrong password, changed ciphertext, changed header, two exports differ, no plaintext in file, unknown version, not an export, KDF read from header | 10 of 10 pass |
| Backup excluded | `allowBackup="false"` plus `data_extraction_rules.xml` excluding cloud backup and device transfer for every domain; `dumpsys package` | No `ALLOW_BACKUP` flag. Rules lint clean |
| Android 16 page size | ELF `LOAD` alignment of `libsqlcipher.so` in the APK, all four ABIs | 16384 bytes. Pass |
| Instrumented run | 8 tests on the emulator | 8 of 8 pass |

Timings on the emulator (slow, x86 under emulation, so only a rough guide): PBKDF2 at 600,000 rounds took about 4.5 s to export and 4.1 to 4.4 s to restore. Argon2id took about 1 s to export and 0.3 s to restore. The Keystore key reported security level `software`.

## Result

The approach works on Android 16: Room and SQLCipher at the pinned versions run together, the key is bound to the device's Keystore, the file is unreadable without it, and a password-protected export restores on a clean install without anything from the old device. BouncyCastle's Argon2 class loads and runs on Android 16 without clashing with the platform copy.

**Limits (why this is not a plain pass):**

1. Emulator only. The Keystore key is software-backed here. On the S25 Ultra and Z Flip 5 it should be in the trusted environment or StrongBox; this needs to be confirmed with `recordsWhereTheWrappingKeyLives`.
2. "Restart" was simulated by closing the database and building a new key provider, not by killing the app process. A real force-stop and reboot check on the phones is still needed.
3. KDF timing must be re-measured on the phones before choosing between PBKDF2 and Argon2id. Pick the one that keeps export and restore under a few seconds on the slower phone.
4. Not tested: key behaviour after a device lock-screen change or biometric enrolment (the key is not tied to user authentication), and a large database (thousands of rows).

## Decision or change this causes

- Open for the user to decide after phone timings: PBKDF2 or Argon2id for the portable export.
